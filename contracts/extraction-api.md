# 추출 API 계약

core(호출자)와 extractor(추출 서비스) 사이의 계약. 구현이 이 문서와 어긋나면 구현을 고친다.
내부망 전용이고 인증은 없다(보안그룹 격리).

| 정본 | 맡는 것 |
|---|---|
| `contracts/extraction.proto` | 엔드포인트 경로, 요청·응답의 모양, 필드와 code 의 의미, code 분류(disposition·bucket), 호출자 read 타임아웃, 몰별 규칙의 모양과 Redis 키, 스트림 메시지와 정책 배포본의 모양·키·시간 값 |
| 이 문서 | 모양으로 표현되지 않는 동작 규칙과 그 근거 |

와이어는 protobuf 의 JSON 매핑이다(필드명 lowerCamelCase, enum 은 이름 문자열).

## 0. 설계 불변식

- Extractor 는 무상태다. 같은 요청이 중복 도착해도 대가는 LLM 비용 한 번뿐이다.
  예외는 몰별 규칙의 배포본을 메모리에 두는 것 하나다(7절). 요청 사이에 남는 것은 그것뿐이다.
- 재시도·내구성·상태 전이는 호출자의 책임이다. Extractor 는 단건 시도 1회에만 답한다.
- 에스컬레이션(plain fetch 에서 헤드리스 브라우저로)은 Extractor 내부 관심사라 응답에 드러나지 않는다.
  브라우저를 여는 데는 허락이 필요 없다.
- 정책 수용 지점은 요청의 `authorized` 와 `blocked_domains` 다. 판정 원장은 호출자이고 Extractor 는 판단하지 않는다.
  스트림 경로(8절)는 같은 값을 정책 배포본에서 읽는다.
- 운영 호출자의 추출은 스트림 경로(8절)로 온다. 1·2·4절의 HTTP 추출 경로는 그대로 열려 있고 응답 규칙도 같다.

## 1. 응답 3갈래

| Extractor 응답 | 의미 | core 전이 |
|---|---|---|
| 2xx + 추출 결과 | 성공 | `markReady` |
| 422 + `{code}` | 확정 실패 | 즉시 `markFailed` |
| 그 외 전부 (5xx·타임아웃·연결 실패·미지의 상태) | 일시 실패 | PROCESSING 유지 후 recover 재시도 (attempt 상한 2) |

- 전이 판정은 HTTP status 만 쓴다. `code` 는 관측용이고, 모르는 code 여도 422 면 확정 실패다.
- 분류할 수 없는 실패는 전부 일시로 떨어진다(fail-safe). 재시도 비용은 호출자의 attempt 상한이 바운드한다.
- code 의 `disposition` 옵션과 1:1 이다. `PERMANENT` 는 422, `TRANSIENT` 는 502.

## 2. 엔드포인트

항목 이름은 proto 의 rpc 이름이고, 경로는 그 rpc 의 `http_post` 옵션이다.

### LinkExtraction

- 지정 모델이 404 면 기본 모델로 대체하고 추출을 이어간다(가용성 우선). 응답 모양은 같고, 대체 사실은
  warn 로그와 `gemini.model.fallback` 카운터에만 남는다.
- 400·5xx·timeout 은 대체하지 않는다. 400 은 요청 쪽 결함일 수 있어 대체가 버그를 덮고, 나머지는 모델을
  바꿔도 풀리지 않는다.
- 헤더 `X-Correlation-Id`(선택)는 호출자의 item_snapshot id 다. 로그 상관용이고 동작에 영향 없다.
- `blocked_domains` 는 요청을 보내기 전에 대조한다. 응답을 받은 뒤 거르면 차단한 곳에 요청이 이미 나간 뒤다.
  같은 목록을 렌더 서비스에도 넘겨 브라우저의 이동도 같은 규칙을 따른다.

### ImageExtraction

- 처리 순서는 `download(bucket, key)`, OCR 추출, bbox 크롭(불가 시 원본), `upload(bucket, items/{uuid}.{ext})` 다.
  업로드한 결과의 public URL 이 `imageUrl` 이다.
- `imageUrl` 은 항상 채워진다(크롭에 실패해도 원본이 올라간다). 이름·가격을 못 뽑으면 그 둘만 빈 200 이다.
- 업로드 확장자·content-type 은 결과물을 따른다. 크롭했으면 png, 크롭 불가 포맷(HEIC·WebP·HEIF)은 원본 그대로다.
- 모델 대체 규칙은 link 와 같다.

### ModelProbe

백오피스가 모델을 저장하기 전에 그 모델이 그 경로에서 실제로 동작하는지 묻는다.

- 판정은 메타 조회가 아니라 그 경로의 실제 generateContent 호출이다. 존재 확인만으로는 요청 스키마
  비호환(400)을 못 거르는데, 400 은 추출 경로에서 대체 대상이 아니라 파싱 전건 실패다.
- 대체 없이 지정 모델만 친다. 대체하면 없는 모델도 기본 모델이 대신 통과시켜 게이트가 무력화된다.
- 아는 모델 목록을 코드에 두지 않는다. 목록을 두면 새 모델마다 Extractor 배포가 필요하다.
- 일시 실패를 거절(422)로 바꾸지 않는다. 외부가 잠깐 흔들린 사이에 멀쩡한 모델의 저장이 막힌다.

| status | 의미 | 호출자의 처리 |
|---|---|---|
| `200` (body 없음) | 이 경로에서 동작하는 모델 | 저장 허용 |
| `422` + code | 확정 거절 | 저장 거부 + 사유 표시 |
| `400` | 필수 필드 누락·모르는 target | 호출자 구현 버그. 재시도해도 같다 |
| 그 외(502) | 외부 사정으로 확인 불가 | 저장 거부 + 재시도 안내 |

### RuleProbe

백오피스가 몰별 규칙을 저장하기 전에 그 규칙이 실제 상품 페이지에서 무엇을 읽는지 묻는다.

- 배포본을 읽지 않고 요청에 실린 규칙 하나만 적용한다. 아직 저장하지 않은 규칙을 시험하는 경로다.
- LLM 을 부르지 않는다. 규칙과 공통 규칙이 각각 읽은 값을 나란히 돌려주고, 채택 판단은 사람이 한다.
- 규칙의 `fetch` 가 `RENDER` 면 렌더한 문서에서 읽는다. 문서를 얻는 흐름과 실패 응답은 LinkExtraction 과 같다.
- 규칙을 해석하지 못하면 실패가 아니라 200 의 `ruleError` 로 답한다. 페이지가 아니라 입력의 문제라 실패 code 의
  분류 축(disposition·bucket)에 들지 않는다.

## 3. bucket (확정 실패의 운영 분류)

값과 뜻의 정본은 `extraction.proto` 의 `Bucket` enum 이다. 확정 실패에만 붙고, 일시 실패는 recover 가
종결 시 집계한다.

## 4. 타임아웃 예산

| 층 | 값 | 근거 |
|---|---|---|
| core 회수 기준 | core `ItemParseOutboxQueue` 의 stuckAfter | 이 시간 지나도 PROCESSING 이면 recover 가 다시 발주 |
| core -> Extractor HTTP read | proto 의 `caller_read_timeout_seconds` (connect 2s) | connect 와 합이 회수 기준 미만(core 가 부팅에서 검사). recover 의 유령 중복 발주 방지. 전 경로 공용 |
| Extractor 내부 합계 (link) | 호출자 read 타임아웃에서 여유를 뺀 값(`ExtractionDeadline`) | 지나면 render·LLM 단계를 새로 시작하지 않음 |
| 대상 몰 fetch (link) | connect 5s / read 15s | |
| 헤드리스 render (link) | connect 2s / read 는 render.proto 의 `caller_read_timeout_seconds` | 실측 전형 1.6-5.5s 대비 약 4배 여유. headless-first 최악(connect + render read + LLM read)이 호출자 read 타임아웃 안에 들도록 상한 |
| Gemini | read 30s | link LLM fallback·image OCR 동일 |
| Extractor 내부 합계 (image) | 약 40s | S3 download + Gemini OCR 30s + crop + 결과 upload |

- 안쪽 예산은 항상 바깥보다 작아야 한다. headless-first 합계와 Gemini read 가 호출자 read 타임아웃보다 작은지는
  Extractor 의 테스트가 대조한다.
- 에스컬레이션 경로(plain 실패 후 headless)의 단일 hop 최악(fetch connect + read, render connect + read, LLM read)은
  호출자 read 타임아웃 안에 든다. 예외는 redirect 누적이다. hop 마다 fetch 타임아웃이 새로 적용돼 fetch 단독 이론
  최악이 약 120s 라 여기에 render 와 LLM read 가 얹히면 넘는다. 넘치면 호출자가 일시 실패로 처리해 재시도하고,
  Extractor 가 무상태라 중복 발주는 안전하다.

## 5. 진화 규칙

- additive-only. 필드·code 추가는 자유, 제거·의미 변경·타입 변경은 금지다(필요하면 새 경로).
  모양 위반은 CI 의 `buf breaking` 이 막는다.
- code 는 proto enum 에 분류 옵션과 함께 더한다. 소비 repo 의 메타 테스트가 자기 매핑과 대조한다.
- 배포 순서는 Extractor 먼저, core 나중. 렌더 계약(`render.proto`)이 함께 바뀌면 renderer 가 Extractor 보다 먼저.
- 호출자는 모르는 응답 필드·code 를 무시한다(tolerant reader).

## 6. 관측

- W3C `traceparent` 헤더를 수용해 core 의 `item.parse` span 아래로 연결된다.
- 추출 메트릭(`product.extract{via,reason}`·`product.extract.escalation{outcome,category}`)은 Extractor 가
  소유한다(`contracts/observability.md`).

## 7. 몰별 규칙

값과 모양의 정본은 `extraction.proto` 의 `ExtractionRuleSet` 이다.

### 보관

| 자리 | 주인 | 역할 |
|---|---|---|
| 운영 호출자의 DB | 운영 호출자 | 원본. 규칙 본문과 변경 이력 |
| 운영 Redis 의 키(`redis_key` 옵션) | 운영 호출자가 쓰고 Extractor 가 읽음 | 배포본. `ExtractionRuleSet` 의 JSON 문자열 하나 |

- 배포본은 운영 Redis 하나고 쓰는 쪽은 운영 호출자뿐이다. Extractor 는 서버 한 대가 모든 환경의 요청을 받으므로
  환경마다 규칙을 나누지 않는다. dev 호출자의 요청에도 같은 규칙이 적용된다.
- 호출자는 규칙이 바뀌면 곧바로 전체를 다시 올리고, 하루 주기로 원본과 대조해 어긋나면 다시 올린다.
- Extractor 는 요청마다 Redis 를 읽지 않는다. 주기적으로 읽어 메모리에 두고, 반영 지연은 그 주기만큼이다.
- 키가 없거나 `rules` 가 비었으면 규칙 0개다. 다음 읽기에 곧바로 반영한다. 잘못된 규칙을 급히 내리는 길이다.
- Redis 에 닿지 못하거나 값을 JSON 으로 해석하지 못하면 직전에 읽어 둔 배포본을 계속 쓴다. 직전 것이 없으면 규칙 0개다.
- 규칙 0개여도 요청은 실패하지 않는다. 추출은 공통 규칙과 LLM 으로 이어진다.
- 해석하지 못하는 규칙 하나는 그 규칙만 버린다. 대상이 없거나 값이 빈 것, 출처가 빈 `FieldSource`,
  선택자 문법 오류가 여기 든다. 모르는 필드는 무시한다(tolerant reader).

### 적용 순서

1. `host` 규칙. 여럿이 맞으면 host 가 가장 긴 것, 같은 host 면 배포본에 먼저 적힌 것.
2. `marker` 규칙. 여럿이 맞으면 배포본에 먼저 적힌 것.
3. 공통 규칙(구조화 데이터와 공통 휴리스틱).
4. LLM.

- 규칙은 한 문서에 하나만 적용한다. 판정 기준은 그 문서를 받은 최종 주소와 그 문서의 내용이다.
- `fetch` 가 `RENDER` 인 `host` 규칙은 입력 주소의 host 가 맞으면 정적 fetch 없이 렌더한다. 이것은 문서를 얻는
  지름길일 뿐이고, 적용할 규칙은 렌더한 문서의 최종 주소로 다시 판정한다.
- 리다이렉트 뒤에야 host 가 드러나는 주소와 `marker` 규칙은 정적 fetch 로 받은 문서에서 대상을 판정한 뒤 렌더한다.
- 규칙이 출처를 적지 않은 필드는 공통 규칙이 채운다. 둘이 같은 필드를 읽으면 규칙의 값을 쓴다.
- 규칙과 공통 규칙이 읽은 필드는 LLM 이 덮지 않는다. LLM 은 빈 필드만 채운다.
- `method` 는 이름·이미지·판매가 가운데 하나라도 LLM 이 채웠으면 `LLM`, 아니면 `STRUCTURED` 다.

### 읽기

- 선택자는 Extractor 가 받아 둔 문서에 적용한다. 그 문서에는 style·주석과 데이터가 아닌 script 가 없다.
  남는 script 는 JSON 계열 type 을 가진 것과 `#__NEXT_DATA__` 다. `script[src]` 를 가리키는 선택자는 맞지 않는다.
- 요소의 글자는 후손의 글자를 문서 순서로 이어 붙이고 앞뒤 공백을 뗀 것이다.
- 가격은 금액 하나로 읽는다. 금액은 숫자와 자릿수 쉼표로 된 양의 정수고, 바로 뒤에 `%` 가 붙은 수와 소수는
  금액이 아니다. 글자에 금액이 없거나 둘 이상이면 값 불량이다.
- JSON 의 가격은 정수거나 위 규칙으로 읽히는 문자열이다. 이름과 이미지는 비지 않은 문자열이다. 그 밖의 타입은 값 불량이다.
- 이미지 주소가 상대 주소면 문서의 최종 주소를 기준으로 푼다. https 가 아니면 값 불량이다.
- 규칙이 읽은 값도 공통 규칙의 값과 같은 신뢰 검증(범위·상식, 정가는 판매가 이상)을 거친다. 걸리면 값 불량이다.

### 못 읽었을 때

못 읽는 경우는 둘이다. 자리 없음은 선택자에 맞는 요소가 없거나, script 는 있는데 pointer 가 가리키는 값이 없거나
null 인 것이다. 값 불량은 자리는 있는데 값을 읽지 못한 것이고, `JsonSource` 의 script 자체가 없는 것도 여기 든다.

| 필드 | 자리 없음 | 값 불량 |
|---|---|---|
| 출처를 적은 이름·이미지·판매가 | 규칙의 값을 전부 버림 | 규칙의 값을 전부 버림 |
| 출처를 적은 정가 | `NO_DISCOUNT` 선언이 있으면 판매가와 같은 값, 없으면 정가만 다음 층으로 | 정가는 모름. 선언을 적용하지 않고 다음 층으로 |

- 규칙의 값을 버리면 그 규칙의 선언도 버리고 공통 규칙부터 다시 읽는다. 몰의 구조가 바뀌었다는 신호라
  Extractor 가 규칙 id 와 못 읽은 필드를 로그로 남긴다. 요청은 실패시키지 않는다.
- 정가 출처를 적지 않은 규칙의 `NO_DISCOUNT` 는 공통 규칙이 정가를 찾지 못했을 때 적용한다.
- `NO_DISCOUNT` 는 판매가를 규칙이나 공통 규칙이 읽었을 때만 적용한다. 판매가가 없거나 LLM 이 읽은 것이면
  적용하지 않는다. 선언의 전제(할인이면 정가를 싣는다)가 그 문서에서 성립하는지 알 수 없기 때문이다.
- 틀린 정가와 틀린 "할인 없음" 은 정가 없음보다 나쁘다. 애매하면 채우지 않는다.

## 8. 스트림 경로

요청·결과·정책의 모양과 스트림 키·소비 그룹·시간 값의 정본은 `extraction.proto` 의 `ParseRequest`·`ParseResult`·
`ExtractionPolicy` 다. 이 절에서 옵션 이름으로 부르는 값은 전부 그 선언에 있다.

### 흐름

1. 호출자가 요청을 자기 DB 에 남기고 `ParseRequest` 를 요청 스트림에 쓴다.
2. Extractor 가 꺼내 추출하고 `ParseResult` 를 결과 스트림에 쓴 뒤 요청에 확인 응답을 보내고 지운다.
3. 호출자가 결과를 꺼내 반영하고 확인 응답을 보내고 지운다.

- Redis 는 환경마다 하나다. Extractor 는 서버 한 대가 모든 환경을 받으므로 환경마다 그 환경의 Redis 에 소비자를 붙인다.
  결과와 정책은 요청을 읽은 그 Redis 에서 쓰고 읽는다.
- 항목의 필드는 메시지의 JSON 필드 이름(lowerCamelCase)이고 값은 전부 문자열이다. enum 은 이름, 수는 십진 표기다.
- 요청 하나의 처리 규칙(모델 대체, 차단 대조, 이미지 처리 순서)은 2절의 LinkExtraction·ImageExtraction 과 같다.
- 결과의 `code` 는 성공이면 `OK`, 실패면 실패 code 의 이름이다. 호출자는 확정 실패와 일시 실패를 다르게 전이하지
  않고 둘 다 실패로 닫는다. 구분은 `disposition` 과 `bucket` 으로 관측에만 쓴다.

### 전달 보장

- 두 스트림 모두 최소 1번 전달이다. 같은 항목이 두 번 올 수 있고 순서는 보장하지 않는다.
- 확인 응답은 일을 끝낸 뒤에 보낸다. Extractor 는 결과를 쓴 뒤, 호출자는 반영을 커밋한 뒤다.
- 확인 응답과 삭제는 한 명령(`XACKDEL`)으로 한다. 스트림에 남는 것은 아직 끝나지 않은 항목뿐이다.
- 중복은 호출자가 거른다. 요청이 진행 중일 때만 결과를 반영하고, 이미 닫힌 요청의 결과는 버린다.
  Extractor 는 중복을 거르지 않는다. 같은 요청을 두 번 처리해도 대가는 추출 한 번의 비용이다(0절).

### 이어받기

- 꺼내 간 소비자가 `redelivery_after_seconds` 안에 확인 응답을 보내지 못하면 같은 그룹의 다른 소비자가 이어받는다.
- 이 값은 추출 한 건의 최대 시간(4절의 Extractor 내부 합계)보다 커야 한다. 작으면 아직 도는 요청을 다시 꺼내 간다.
  Extractor 가 기동 때 검사한다.
- `max_deliveries` 번 꺼내 가고도 끝나지 않은 항목은 더 추출하지 않고 `DELIVERY_EXHAUSTED` 결과를 쓴 뒤 지운다.
  처리 중에 서버를 죽이는 요청이 끝없이 도는 것을 막는다.
- 입력 종류를 모르는 요청은 추출하지 않고 `DELIVERY_EXHAUSTED` 결과를 쓴 뒤 지운다.
- 요청 번호를 읽을 수 없는 요청은 결과를 쓸 수 없어 로그만 남기고 지운다.

### 기한

- 호출자는 요청을 만든 지 `result_deadline_seconds` 가 지나도록 결과가 없으면 스스로 실패로 닫는다.
  다시 보내지 않는다. 늦게 온 결과는 닫힌 요청의 결과라 버려진다.
- 이 값은 정상 경로의 최악보다 커야 한다. 최악은 호출자의 첫 전송 지연, 이어받기 대기와 주기를
  `max_deliveries - 1` 번, 추출 한 건의 최대 시간을 `max_deliveries` 번 더한 값이다. 호출자가 기동 때 검사한다.
- 요청이나 결과가 Redis 에서 사라진 경우를 닫는 장치는 이것뿐이다.

### 정책 배포본

| 자리 | 주인 | 역할 |
|---|---|---|
| 각 환경 호출자의 DB·설정 | 그 환경의 호출자 | 원본 |
| 각 환경 Redis 의 키(`redis_key` 옵션) | 그 환경의 호출자가 쓰고 Extractor 가 읽음 | 배포본. `ExtractionPolicy` 의 JSON 문자열 하나 |

- 몰별 규칙(7절)과 달리 환경마다 따로다. 모델·신원·차단 목록·버킷이 환경마다 달라서다.
- 호출자는 값이 바뀌면 곧바로 전체를 다시 올리고, 주기적으로 원본과 대조해 다시 올린다.
- Extractor 는 요청마다 읽지 않는다. 주기적으로 읽어 메모리에 두고, 반영 지연은 그 주기만큼이다.
- 키가 없으면 정책은 전부 기본값이다. 기본 모델, 기본 신원, 차단 0개, 허락 0개, 버킷 없음.
- Redis 에 닿지 못하거나 값을 해석하지 못하면 직전에 읽어 둔 배포본을 계속 쓴다. 직전 것이 없으면 기본값이다.
- 버킷이 없으면 IMAGE 요청은 `DELIVERY_EXHAUSTED` 로 닫는다. LINK 요청은 기본값으로 처리한다.
- 차단 목록이 기본값이면 Extractor 는 어떤 도메인도 막지 않는다. 입력 주소의 차단은 호출자가 요청을 쓰기 전에
  한 번 더 건다. Extractor 의 대조는 옮겨 간 주소를 위한 것이다.
