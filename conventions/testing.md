# 테스트 컨벤션 (원칙)

**정본.** `install.sh` 가 소비 repo 의 `.claude/rules/testing-principles.md` 로 설치하고, 각 repo 의 `CLAUDE.md` 가 그것을 import 해 자동 로드한다.

이 문서는 **언어·스택에 무관한 원칙**만 담는다. 문법·도구에 묶이는 결정(테스트 메서드 네이밍 방식·단언 라이브러리·DB 컨테이너 필요 여부·메타 테스트 구현체)은 각 repo 가 자기 바인딩 문서에 둔다. 같은 원칙이 Kotlin 과 Java 에서 다른 모양으로 구현되는 것은 어긋남이 아니라 정상이다.

- **1장 — 스택 무관 원칙**: 어느 언어에서든 그대로 적용된다.
- **2장 — JVM · Spring 공통**: 현재 소비 repo 두 곳(core · extractor)이 모두 Spring 이라 공유한다. 다른 스택 repo 가 소비하게 되면 그 repo 는 1장만 따른다.
- **3장 — 각 repo 가 소유하는 것**: 여기 두지 않는 것의 목록. 무엇을 자기 repo 에서 찾아야 하는지 알려준다.

---

## 1장. 스택 무관 원칙

### 테스트 분류

테스트는 **세 종류**를 기본으로 둔다 — 단위 · 통합 · E2E. 두 축으로 갈린다: **무엇을 검증하나**(분기 망라 vs 시나리오·계약), **외부 의존성을 실제로 타나**(stub 격리 vs 실제 호출).

- **단위** — 프레임워크 컨텍스트 없이 도메인 객체와 순수 함수만 검증. 부팅 비용이 0 이라 가장 빠르다. 입력 형식 / 정규화 / 상태 변화 / 계산 등 **분기 폭이 큰 영역은 전부 여기서 망라**한다.
- **통합** — 진입점(HTTP)부터 저장소까지 실제 흐름을 검증. 외부 호출(LLM · HTTP fetch · 결제 등)은 **stub 으로 격리**한다. 외부를 실제로 타지 않는다.
- **E2E** — 외부 의존성을 **stub 없이 실제로 호출**해, stub 가정과 현실의 어긋남을 확인한다. 네트워크 비결정성·외부 차단 탓에 **CI 기본 실행에서 제외**하고 환경변수·비활성 어노테이션으로 격리한다.
- **직렬화/호환성 (조건부)** — 캐시·저장소에 **객체를 직렬화해 저장할 때만** 둔다. 무중단 배포 중 구·신버전이 같은 저장소를 공유하므로, 한쪽이 쓴 객체를 다른 쪽이 못 읽으면 런타임 장애다. 직렬화 스냅샷을 고정해 두고 현재 결과가 그것과 호환되는지 검증한다.

**서비스 단독 테스트는 두지 않는다.** 분기는 도메인으로 옮겨 단위로 내리고, 시나리오·계약 검증은 통합으로 흡수한다. 서비스에 분기가 쌓이면 **도메인 모델이 빈약(anemic)** 하다는 신호다.

시간 · 동시성 · 트랜잭션 경계처럼 일반 통합 패턴으로 표현이 어려운 경우, 기본 분류에 욱여넣지 말고 **별도 분류를 명시적으로 만든 뒤** 추가한다.

### 테스트 가치 판단 (무엇을 테스트하는가)

분류가 "어디서 테스트하나"를 답한다면, 그 앞에 "이걸 테스트할 가치가 있나"를 먼저 판단한다. 모든 코드에 테스트가 필요하지 않다 — 핵심 20% 에 집중해 신뢰의 80% 를 얻는다.

**기준 한 줄: 커버리지 숫자가 아니라 "깨지면 비싼가 + 회귀 위험이 큰가 + 읽기·변경이 잦은가".**

| 가치 | 무엇 | 어디서 |
|---|---|---|
| 높음 (반드시) | 도메인 정책·계산·상태 전이 (분기 큰 것) | 단위 |
| 높음 (반드시) | 핵심 유저 여정 | 통합 |
| 높음 (반드시) | 진입점 계약 (응답 모양·예외 매핑) | 통합 |
| 높음 (반드시) | 외부 의존성 분기 (성공/실패/timeout) | stub 통합 |
| 낮음 (생략·수동) | 단순 위임·getter·자명한 매핑, 프레임워크가 보장하는 것 | — |
| 낮음 (생략·수동) | 수명 짧은 이벤트성 기능 | 수동 테스트로 대체 |

가치가 낮다고 판단해 생략하면 **그 판단(왜 안 하나)을 PR·코드에 한 줄 남긴다.** "빠뜨린 것"과 "의도적으로 안 한 것"을 구분하기 위해서다.

### 분기 위치 결정 트리

```text
이 분기는 무엇을 검사하는가?

(1) 입력 형식 · 값 범위 · null · 정규화
    → 도메인 객체 생성자 / 팩토리 안 → 단위
(2) 상태 변화 · 계산 · 정책
    → 도메인 객체 메서드 안 → 단위
(3) DTO ↔ 도메인 매핑 · 정규화
    → 매퍼 함수 → 단위
(4) "저장소 상태 + 결정" (예: "이미 존재하는가?")
    → 통합
(5) 진입점 계약 (입력 검증 · 예외→상태 매핑 · 응답 모양)
    → 통합
(6) 외부 API 호출 결과 분기 (성공 / 실패 / timeout)
    → 외부 호출 stub + 통합
(7) 실제 외부 의존성과의 접점 (어느 대상이 파서/LLM/차단인가 등)
    → stub 없이 실제 호출 → E2E (환경 격리 · CI 제외)
(8) 직렬화해 저장한 객체의 배포 간 호환성
    → 스냅샷 비교 → 직렬화/호환성 테스트
```

### 모킹 / stub 정책

**내부 컴포넌트는 모킹·stub 모두 금지하고 실제 구현으로 통합 테스트한다.** 외부 호출 경계(외부 HTTP API · 메시징 · 결제 등 우리 애플리케이션 바깥)만 격리하며, 격리 도구로 **프로그래머블 stub 을 기본**으로 한다.

- 외부 경계는 인터페이스로 두고 **stub 구현**을 만들어 등록한다. stub 의 응답을 람다·필드로 받아 매 테스트가 시나리오별로 교체한다.
- **stub 의 기본 동작은 throw 로 둔다.** 동작 가능한 기본값을 두면 명시 세팅을 빠뜨려도 통과해버린다. 기본을 throw 로 두면 세팅 누락이 즉시 깨져 "이전 테스트의 세팅이 살아남는" 함정을 차단한다.
- 호출 검증이 필요하면 stub 에 카운터·기록 필드를 더한다 (`verify` 와 동등).
- 진입점(컨트롤러) 테스트도 서비스를 모킹·stub 하지 않는다. 실제 흐름을 통과시킨다.

**왜 stub 이 mock 보다 나은가**

- **시그니처 변경 안전** — stub 은 인터페이스 구현이라 컴파일 타임에 깨진다. mock 은 reflection 기반이라 이름 오타·시그니처 변경이 런타임에야 드러난다.
- **컨텍스트 캐시 보존** — stub 은 한 곳에 등록되어 모든 테스트가 같은 인스턴스를 공유한다 (2장 참조).
- **디버깅 용이** — 실제 인스턴스라 디버거에서 내부가 보이고 IDE 의 참조 탐색이 동작한다.
- **표현력 동등** — 람다 교체로 시나리오별 동적 응답이 가능하다.

**왜 내부는 금지인가**: 모킹·stub 은 본질적으로 "이 호출이 이렇게 동작한다"는 **가정 코드**다. 가정과 실제의 어긋남이 통합 시점에 드러나면 가장 비싸다. 내부를 모킹하면 리팩터링이 깨져도 테스트는 초록불을 유지하는 사고가 잦다.

### 테스트 셋업 원칙

**셋업 hook 으로 fixture 데이터·stub 상태·인프라 객체를 미리 채우지 않는다.** 각 테스트 메서드가 자기 시나리오에 필요한 것을 본문에서 직접 만든다.

- 공유 mutable 상태(stub 의 람다 등)는 매 테스트가 명시적으로 세팅한다. 셋업 hook 에서 기본값으로 되돌리는 구조도 금지.
- 저장소 격리는 트랜잭션 자동 롤백 등 프레임워크 수단으로 해결하고, 정리 코드를 hook 에 두지 않는다.
- **이유**: 테스트 메서드 하나만 봐도 시나리오를 완전히 이해할 수 있어야 한다. 셋업 hook 은 한 테스트의 변경이 다른 테스트로 누수되는 함정을 만들고, "암묵적 사전 상태"가 회귀 추적·리뷰 비용을 올린다.

### 네이밍

**분류가 파일명에 드러나야 한다.** 파일명이 분류의 single source 이고, 기계 강제(아래)가 파일명으로 분류별 규칙을 적용한다.

| 분류 | 접미사 |
|---|---|
| 단위 | `{대상}Test` |
| 통합 | `{기능·시나리오}IntegrationTest` |
| E2E | `{대상}E2ETest` |
| 동시성 | `{대상}ConcurrencyIntegrationTest` |
| 타이밍 | `{대상}TimingIntegrationTest` |
| 직렬화(조건부) | `{대상}SerializationCompatibilityTest` |

통합 테스트는 단일 클래스가 아니라 시나리오를 검증하므로 대상 클래스명 하나로 짓지 않는다.

**메서드명은 시나리오를 한국어 한 문장으로 표현한다.** 그 문장을 어디에 두느냐(메서드명 자체 vs 별도 표시 어노테이션)는 언어 문법에 달렸으므로 각 repo 바인딩이 정한다.

### 기계 강제와 그 한계

**기계로 오탐 없이 판정 가능한 불변식은 산문에 두지 말고 테스트로 내린다.** 소스를 스캔해 금지 패턴·필수 어노테이션을 검사하는 메타 테스트를 두고, 그것을 CI 필수 체크에 포함시켜 위반이 머지 전에 빨간불로 드러나게 한다.

- **승격 기준은 횟수가 아니라 판정 가능성이다.** 오탐 없이 PASS/FAIL 을 가를 수 있으면 기계로, 사람·모델 판단이 끼면 산문으로 남긴다.
- **정본은 코드다.** 산문 요약과 메타 테스트가 어긋나면 코드가 이긴다. 규칙을 바꿀 때는 산문을 먼저 고치고 메타 테스트를 따라 고친다.
- **한계를 명시한다.** import 텍스트 스캔 방식은 풀패키지 인라인 참조나 denylist 에 없는 새 라이브러리를 못 잡는다. 타입 그래프 수준의 강제가 필요하면 전용 도구로 승격해야 하며 그건 별도 작업이다.
- **자기 참조의 한계**: 메타 테스트 자체를 약화·삭제하는 변경은 약해진 채로 CI 가 초록불이다. 코드로 자기무결성을 완전히 보증할 수 없으므로 **그 파일의 변경은 사람 리뷰가 책임진다.**

## 2장. JVM · Spring 공통

현재 소비 repo(core · extractor)가 모두 Spring 이라 공유한다. 다른 스택 repo 는 1장만 따른다.

### 단일 컨텍스트 공유 (컨텍스트 캐싱 보존)

**모든 통합 테스트는 단일 베이스 클래스의 컨텍스트를 공유한다.** 컨텍스트가 한 번만 부팅되고 캐시 재사용되어 빌드 시간이 크게 줄어든다. Spring 은 **빈 그래프가 다르면 새 컨텍스트를 부팅**하므로, 아래를 전부 금지한다.

- 클래스별 `@Import` / `@TestConfiguration` / `@MockBean`(`@MockitoBean`·`@SpyBean`·`@TestBean` 포함) 으로 컨텍스트 변형
- `@DirtiesContext` — 캐시를 폭파해 다음 테스트가 재부팅 비용을 부담한다
- `@ActiveProfiles` · `@TestPropertySource` · `@SpringBootTest(webEnvironment=...)` 로 클래스별 분기 — 전부 별개 컨텍스트로 캐싱된다

**`@SpringBootTest` 는 베이스 클래스 한 곳에만 선언한다.** 외부 stub 빈도 한 곳에 모아 등록해 모든 통합 테스트가 같은 인스턴스를 공유한다.

**stub 빈에는 `@Primary` 를 붙인다.** 운영 빈과 타입이 같아 주입 후보가 둘이 되는데, 빈 이름과 파라미터명이 우연히 일치하는 데 기대면 파라미터명 리팩터링 시 격리가 조용히 깨진다. `@Primary` 가 그 의존을 끊는다.

### E2E 격리 (필수)

E2E 클래스는 둘 중 하나를 **반드시** 둔다.

- `@EnabledIfEnvironmentVariable(named = "...", matches = ".+")` — 환경이 있을 때만 실행
- `@Disabled("이유 명시")` — 영구 비활성, 수동 실행 시 해제

**둘 다 없는 무방비 E2E 는 금지** — CI 에서 실제 외부 호출이 돌아 flaky·비용·외부 차단을 유발한다. 이 규칙은 기계 강제 대상이다.

E2E 는 통합 테스트의 베이스 클래스를 **상속하지 않는다.** stub 컨텍스트가 실제 호출을 가리기 때문이다.

### 동시성 · 시간 의존 테스트

race · 동시성 · timeout 은 "검증이 어려우니 생략" 으로 귀결시키지 않고 별도 분류로 명시적으로 작성한다.

- 베이스 클래스는 그대로 상속해 컨텍스트 캐시를 보존하되, **클래스 레벨 `@Transactional` 은 쓰지 않는다** — 별도 트랜잭션의 동시 진행이 시뮬레이션의 본질이기 때문.
- 데이터 격리는 자기가 만든 행을 명시적으로 정리하거나, 매 테스트가 격리된 식별자(새 UUID 등)를 쓴다.
- 동시 호출은 `ExecutorService` + `CountDownLatch` 로 **동시 출발을 강제**한다. `Thread.sleep()` 으로 타이밍을 맞추지 않는다.
- timeout 검증은 `@Timeout` 또는 Awaitility 를 쓴다. wall clock 차이 비교 금지.

## 3장. 각 repo 가 소유하는 것

아래는 언어·스택에 묶이므로 이 문서에 두지 않는다. 자기 repo 의 바인딩 문서에서 찾는다.

| 항목 | 왜 repo 소유인가 |
|---|---|
| 테스트 메서드명 표기 | Kotlin 은 backtick 식별자가 되고 Java 는 안 된다 (표시 어노테이션으로 대체) |
| 단언 라이브러리 기본값 | 언어별 표준·관용이 다르다 |
| DB 컨테이너 필요 여부·실행 가드 | DB 를 쓰는 repo 만 해당한다 |
